# Executed Role and Knowledge Trace

Status: reviewed historical synthesis candidate
Last verified: 2026-08-05
Scope: representative public-safe run evidence; no private source text

This trace explains how previously executed work becomes the normalized role architecture. It preserves the parts that repeatedly produced reliable outcomes and rejects role names, models, or tools as implied authority.

## Requirements, market, ICP, and pain evidence

Earlier PRD work used source inventory, context digest, requirement drafting, task translation, knowledge update, and review. Later ICP and market work added source grades, account/cohort evidence, role currentness, economics assumptions, disconfirming evidence, and a rule that a signal is not automatically pain or demand. Runs that combined maker and reviewer left an explicit assurance gap; later work restored strategy/evidence makers, GTM/validation makers, an integrator, and an independent reviewer.

**Architecture result:** these functions become one `requirements_and_market_research` role with internal read-only branches. Its canonical output is a reviewed requirement set with claim state, market boundary, non-goals, acceptance, conflicts, owner, reviewer, freshness, and action constraints. PRD and ICP are projections.

## Qualification, outreach, and messages

Qualification work reconciled eligible records, current stage, assignment, current role, and already-existing state before drafting. Message work followed `pain -> bounded mechanism -> low-pressure question`, maintained role-specific variants, checked claim lineage, and separated preparation from sending. Partnership, evidence, and humanization review occurred before exact-scope writeback; post-write readback verified the target.

**Architecture result:** `qualification_and_channel_planner` proves target/currentness and prepares the channel packet; `positioning_and_copy_maker` drafts evidence-linked messaging; `independent_reviewer` controls acceptance; `external_action_operator` acts only after exact approval. The same action validator used for code applies to communication.

## Publication creative and designer

Publication runs used separate evidence, copy, visual-system, rights/source, and automation lanes. One bounded design maker changed the shared Figma or document surface; a different reviewer inspected frozen output. Accepted work required a content job, source/rights boundary, typography/layout constraints, phone-scale checks, recoverability, and an explicit absence of publication authority. Repair was assigned back to the maker and re-reviewed.

**Architecture result:** `designer` is a first-class role that owns visual specification, editable artifact, accessibility/layout proof, and rollback-safe output. It never inherits claim acceptance, rights approval without evidence, publication, or self-review. The `release_operator` remains separate.

## Maker, verifier, reviewer, integrator, librarian

Across code, documents, creative, and outreach, the durable pattern was: a maker creates one bounded candidate; a verifier performs deterministic/readback checks; an independent reviewer issues `APPROVE`, `REVISE`, or `BLOCK`; the integrator controls files, merge order, shared mutation, final receipts, and handoff; the librarian promotes only accepted reusable meaning. Retrieval output and successful commands were never durable truth by themselves.

**Architecture result:** maker/reviewer separation is required for substantial or high-risk work. Integrators cannot self-approve. Librarians retain source, decision, requirement, case, owner, freshness, contradiction, and supersession lineage and reject raw traces or one-off case details.

## Onboarding support

The previous knowledge work already distinguished retrieval from durable memory and source availability from authority. The new onboarding role adds a formal employee projection: current requirement, rationale, source, owner, freshness, contradiction, allowed actions, reviewer, and smallest next task. A request for action becomes a proposal; the agent never silently acts or inherits the source author's permissions.

**Architecture result:** `onboarding_guide` answers source-visibly and proposes; `action_validator` checks; maker/reviewer roles deliver; `knowledge_librarian` promotes only the accepted reusable delta.

## Historical sources sampled

The architecture audit sampled public-safe PRD/ICP dry runs, onboarding research and document packages, qualified-outreach and pain-evidence runs, brand/content redesign, social publication rebuilds, visual-system audits, Figma/document reviews, knowledge readback, and the current E1–E8 role/workflow contracts. The complete source register and FACT/INTERPRETATION/GAP analysis is preserved in the architecture run lane.
