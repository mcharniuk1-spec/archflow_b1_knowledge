# Operations Guide

Status: current Knowledge Operator workflow

## One operating surface

The Knowledge Operator projects one bounded case across documentation, project framing, functional roles and skills, setup, evidence, and the Communication Center. Its browser-local state is a preparation aid. It is not an authenticated identity, shared database, durable memory store, runtime event stream, or action receipt.

Use the five primary destinations in order when the work is unfamiliar:

- **Documentation** explains the problem, public boundary, five-stage loop, and four architecture schemas.
- **Project** frames the objective, decision, evidence boundary, exclusions, expected output, reviewer, and stop conditions.
- **Roles & Skills** selects the smallest functional responsibility and portable method set that can own the output and its checks.
- **Setup** separates the zero-key core from optional local validation, authentication, providers, observability, and writeback.
- **Evidence** shows exact fixture results, denominators, limitations, proof states, and receipt requirements.

Jarvis is a focused intake surface. It validates one public-safe work packet and returns it in the same browser tab to **Communication Center**. The packet carries context, not authority.

## Case sequence

1. **Research:** admit an exact source set, retrieve narrowly, verify exact passages, and keep facts, interpretations, hypotheses, contradictions, and gaps separate.
2. **Define:** name the decision, current requirement, acceptance checks, authority, owner, reviewer, tool and source limits, retry cap, and stop conditions.
3. **Act:** choose the smallest responsible role pack and produce a bounded candidate. Provider use and external effects remain separate gates.
4. **Review:** freeze the candidate, run deterministic checks, and obtain an independent approve, revise, or block verdict.
5. **Remember:** promote only reusable conclusions with provenance, owner, freshness, and supersession; exclude raw conversation exhaust and personal context.

If one approved external action is required, insert it after review and before memory promotion:

```text
reviewed candidate
  -> exact target and authority check
  -> rollback and replay protection
  -> target-specific approval
  -> one bounded action
  -> exact readback
  -> result receipt
```

A successful command or model response is never the receipt by itself.

## Individual and team operation

An individual may coordinate multiple role contracts, but high-risk maker and independent-review responsibilities remain logically separate. Browser drafts stay on that device until exported.

A team assigns the same functional role IDs to people or compatible runtimes. Keep one writer per shared target, declare handoff order, and require the reviewer to work from a frozen candidate. The static dashboard is not shared collaboration; hosted tenancy, RBAC, persistence, retention, backup, and recovery need separate proof.

## Communication Center

Every packet must answer:

- Why is the work needed, and which decision does it support?
- Which sources are allowed, excluded, current, contradictory, or missing?
- Who owns each output, check, approval, and handoff?
- What exact artifact will be produced, and how is it accepted?
- What may the tools change, and what must remain untouched?
- When must the work stop or escalate?
- Which reusable conclusion, if any, is eligible for maintained memory?

The Communication Center records browser-local notifications honestly. “Packet prepared” means a packet was prepared; it does not mean an agent ran, a provider was called, a file changed, a deployment happened, or an external target accepted the result.

## Interrupts and recovery

Stop for a missing owner or reviewer, a stale or private source without authority, a material contradiction, overlapping writers, repeated evidence gaps, exhausted retry or budget limits, credentials, provider spend, Git mutation, deployment, publication, irreversible change, or any external communication.

Resume only with a JSON-safe decision that names the exact target and allowed effect. If readback cannot be performed, the result remains unknown.

## Knowledge promotion

After acceptance, the Knowledge Librarian searches for duplicates and prepares a solution or action-memory candidate. It records the source, supported decision, outcome, owner, review date, freshness rule, and supersession link. Secrets, identities, raw prompts, private source text, temporary preferences, and unreviewed model output stay out.
